# Reminders Module

> Developer guide (Vietnamese): [`README.md`](../../../docs/modules/reminders/README.md)

## Purpose

Scheduled reminders delivered as a Zalo message, by default to the owner's private chat, or to a chosen group with chosen people (see [Reminder targets](#reminder-targets)). Reminders are created from chat (LLM tool `SET_REMINDER`, confirmation-gated) or from the dashboard, listed/edited there, and fired by a BullMQ background job. A reminder belongs to its creator (`user_id`): `/reminders` lists only the user's own.

## Reminder times

A reminder (like a task, see [`tasks/README.md`](../tasks/README.md#task-reminders)) reminds at **one or more times**, max `REMINDER_TIME_LIMITS.MAX_TIMES` = 10: rows of `reminder_times` (`id`, `reminder_id` → cascade, `remind_at`, `sent_at`; `timestamp` without time zone like `reminders.remind_at`, so migrated values read back unchanged; index `(sent_at, remind_at)`). Migration `1724940000000-CreateReminderTimes` copied each existing reminder into one row (`sent_at` = `completed_at` for triggered ones). `reminders.remind_at` is the next time not sent (a summary, so lists, the Home payload and `/reminders` in chat keep sorting by it).

- Shared pure logic `reminder-times.ts`: `planReminderTimes(current, requested, now, { allowPast })` (requested = `{ at, repeat? }`; keep times already saved with their sent flag, remove the rest, add new with their repeat (none when not given); `repeatChanges` = kept times whose repeat changes; max 10), `plannedRepeats`, `nextPendingReminderAt` (includes pending reminders again), `lastSentReminderAt`, `toReminderTimeItems` (adds `repeatType`/`repeatWeekdays` of repeating times), `asRequestedTimes`, `revivePayloadTimes` / `payloadTimeAt` / `payloadTimeRepeat` (bot payload times after the Redis round trip). API bodies: `parseRemindTimesBody` (`reminder-rule.body.ts`: `remindTimes` items are ISO strings or `{ remindAt, repeatType?, repeatWeekdays? }`; wins over the single legacy `remindAt`, where `''` clears).
- Personal reminders pass `allowPast: true`: the server never refused a past time (it goes out on the next tick); the dashboard form checks it. Task reminders do refuse new past times.
- See [Repeat & remind again](#repeat--remind-again): each time has its own repeat; reminding again is shared by the reminder.
- Snooze moves the **next** time not sent: API `snoozeReminder` (+N minutes from now, unused by routes); the dashboard Snooze button PATCHes `remindTimes` with that time + 15 minutes (`snoozeReminderTimes`); a repeating next time is kept and the snooze is an extra one-off time.
- Editing `remindTimes` keeps saved times (and their sent flag); at least one time is required (400 otherwise).

## Repeat & remind again

Shared by reminders and task reminders (`apps/api/src/reminders/reminder-schedule.ts`, pure, unit-tested; migration `1724960000000-AddReminderRepeatAndNag`).

- **Repeat, per time** (`reminder_times` / `task_reminder_times`: `repeat_type` `none|daily|weekdays|weekly|monthly`, `repeat_weekdays smallint[]`, `anchor_at`): `nextOccurrence(current, anchor, repeat, now)` in Vietnam time (UTC+7, no DST): daily +1 day; weekdays Mon–Fri; weekly on `repeat_weekdays` (0 = Sunday; empty = the anchor's weekday); monthly on the anchor's day of month (last day of shorter months, back to the anchor day afterwards). Occurrences missed while down are skipped. A repeating time is never marked sent; it moves `remind_at` forward (keeping `anchor_at`). The migration copied each reminder's old `repeat_type` (`daily`/`weekly`) to its times. `reminders.repeat_type` is legacy (written as the repeat of the earliest time by `refreshReminderSummary`; `repeatType` in create/update bodies = repeat of times given without one, and on PATCH without `remindTimes` = repeat of every time).
- **Remind again, per task / reminder** (`nag_every_minutes` 5–1440, `nag_count` 1–10, both or neither; `REMINDER_NAG_LIMITS`): after each send of a time, `nag_at = sent + every`, `nag_left = count`; each reminder again counts down. Must end before the next occurrence of every repeating time it applies to (`validateReminderRule` in contracts / `checkReminderRules`: `every × count` < shortest gap; weekly with several days = smallest gap between them) ⇒ else 400 `Nhắc lại phải kết thúc trước lần lặp kế tiếp.` `null` turns it off (clears `nag_at` of every time). Stops for good when the task is done or the reminder is marked done (`markCompleted` / `status: completed` clear `nag_at`).
- **Due & claim**: a time is due when `(sent_at IS NULL AND remind_at <= now) OR nag_at <= now` (`dueOccurrence`: the time itself first). Claiming is a conditional UPDATE on the state as read (`claimedState`; time: `sent_at IS NULL AND remind_at = read`, reminder again: `nag_at = read`), so overlapping scans never send twice. `releasedState` gives a claimed send back (queueing failed, or ZCA logged out before delivery). A one-off reminder is done only once its times went out and no reminder again is pending; a reminder with a repeating time never finishes by itself.
- **Delivery jobs**: one per send: jobId `…-<ms>` plus `-nag-<k>`; payload `{ timeId, remindAt, nag?: { index, total } }`; a reminder again gets the header line `reminderRule.nagMessage` ("🔁 Nhắc lại 2/3", `withNagLine`).
- **Repeat change on a kept time** (`repeatChangeState`): only the repeat changes; a one-off time that already went out and now repeats restarts at its next occurrence.

## Reminder targets

Shared by personal reminders and task reminders ([`tasks/README.md`](../tasks/README.md#task-reminders)) so the "where and who" is built once. A target is `{ chatId, users: [{ id, name }], mode }` (`apps/api/src/reminders/reminder-target.ts`).

- `chatId`: a Zalo group or private chat. Default: personal reminder → the owner's private chat; task reminder → the chat the bot was asked in. `hasZaloAccount` is false for `dashboard-owner` and for a legacy official-bot id (20 hex chars with a letter, `isLegacyZaloBotId`, `users/legacy-zalo-bot-id.ts`): such users have no private chat (no `isSelf` channel) and must pick one ⇒ else 400 `Chọn kênh Zalo nhận nhắc.`
- A newly chosen chat must be the actor's own private chat, the chat the bot was asked in, or a listened thread (`zca_thread_configs.is_listened`) ⇒ else 400.
- `users`: people of that **group** to remind, max `REMINDER_TARGET_LIMITS.MAX_USERS` = 10, stored with their tag name. Dashboard picks are validated against the group's member list (`ZcaService.getGroupMembers`, cached; ZCA logged out ⇒ 400); bot tags are taken from the message's real Zalo mentions, never guessed from names. **A group target needs at least one person** (`resolve` ⇒ 400 `Chọn ít nhất một người được nhắc trong nhóm.`; checked only when a target is created or changed, so older group rows without people still deliver and still save edits that keep their target). A private chat stores no people: it reminds its own person. Moving to another chat drops them (a new group then needs its own picks).
- `mode` (`ReminderTargetMode`): `mention` (default) = one message in the group tagging the people; `direct` = a private message to each (`reminderTarget.directIntro`: "You are reminded in <chat>"), and whoever cannot be messaged privately (often: not a Zalo friend of the bot account) is tagged in one fallback group message. Without people the mode is always `mention`.
- Changing the chat, the set of people or the mode **never re-sends** a time that already went out; it only applies to times not sent yet.
- Delivery skips (and logs, no retry) a group the admin stopped listening to, the `dashboard-owner` pseudo-chat and a legacy official-bot id (ZCA cannot message it; older rows with `chat_id` NULL of a legacy-id owner land here). Fix such rows by merging the legacy user into the ZCA uid (users module, which also moves `chat_id`) or by picking a chat.

Code: `ReminderTargetService` (`reminder-target.service.ts`, exported by `RemindersModule`): `listChannels`, `listMembers`, `chatNames`, `isListenedThread`, `isUnlistenedGroup`, `resolve(input, current, actor, 'origin' | 'self')`, `deliver(target, { header, body }, locale)`. Pure helpers in `reminder-target.ts`: `buildReminderMessage` (tag line between header and body, `pos`/`len` in UTF-16 units as `zca-js` expects), `normalizeTargetUsers`, `parseTargetUsers` (Redis JSON), `isSameTarget`, `isReminderTargetMode`. `ZcaMessengerService.sendMessageWithMentions` sends one tagged message (not chunked; over the chunk length it goes out untagged).

HTTP (`ReminderTargetsController`, `@Controller('reminder-targets')`, any signed-in dashboard user):

| Method | Route (`API_ROUTES`) | Behavior |
| --- | --- | --- |
| GET | `reminderTargetChannels` | the user's private chat (`isSelf`, Zalo users only) then every listened thread |
| GET | `reminderTargetMembers(chatId)` | members of a listened group (`[{ id, name }]`); 400 for other chats or when ZCA is logged out |

Any dashboard user thereby sees the names of listened threads and their members (before, only admins saw members).

## Web UI (`RemindersScreen`)

- Two tabs (chips, `aria-pressed`): **Upcoming** (default) and **Done**. The tab lives in the URL (`/reminders?status=done`; `upcoming` is left out) via `reminderListStatusFrom` / `writeReminderListStatus` (`apps/web/src/modules/reminders/model/reminder-list-status.ts`), so reload and shared links keep it; the page is wrapped in `<Suspense>` (static export + `useSearchParams`). Switching tab cancels an inline edit.
- Data source: `useRemindersQuery(status)` (key `['reminders', status]`; mutations invalidate `['reminders']`, so both tabs refresh). Only the Upcoming tab falls back to `dashboard.data.reminders` when the list is empty (the Home payload has upcoming reminders only); Done shows `reminders.noDone`.
- `DataPanel` with row counter and client search by title (within the open tab).
- Create: `+ Add reminder` toolbar button (desktop, `max-[960px]:hidden`) / `MobileActionBar` (compact) opens `CreateReminderDialog` with title, reminder times (`ReminderTimesField`: one `datetime-local` per time with its own **repeat** select (`REMINDER_REPEAT_TYPES`) and, for weekly, Mon–Sun toggles; sent as `remindTimes: [{ remindAt, repeatType, repeatWeekdays }]`), **Remind again** (`ReminderNagFields`: checkbox, every `REMINDER_NAG_EVERY_OPTIONS`, at most 1–10; `nagTooLong` error), notify type and the target (`ReminderTargetFields`; private chat preselected; `dashboard-owner` must pick). `Call` is disabled unless the target is the user's own private chat (`reminders.notifyType.callPrivateOnly`). Save is disabled while invalid or in the past; validity is re-checked against the clock on submit. API errors stay in the dialog; success closes it with a toast.
- Columns: title, notify type (`text` / `call`), schedule (`remindAt`), Done tab only `completedAt` ("Done at", `showCompletedAt`; the phone row shows it as trailing value instead of the schedule), repeat (the distinct repeats of the times, else "none", plus "again every … ×N"), `target` (Sent to, `showTarget`, this page only: `ReminderTargetSummary`, `chatName` else "My private chat"), actions.
- Inline edit (title, times with their repeats via compact `ReminderTimesField`, notify type, remind again via compact `ReminderNagFields` in the repeat column, target via compact `ReminderTargetFields`) with Save/Cancel; times are sent when an instant or a repeat changed (`isReminderTimesChanged`), the rule when changed (`isNagChanged`); target fields are sent only when changed (`isTargetChanged`); API rejections show their message in a toast; Snooze = PATCH `remindAt` + 15 minutes (Upcoming tab only: a finished reminder has no next time); editing a finished reminder's times to a future time moves it back to Upcoming (API rule below); Delete asks `window.confirm`. Toasts on save/snooze/delete.
- Error state: alert strip with Retry (invalidates reminders + dashboard caches). Loading is passed to the table.

## Backend API (`RemindersController`, `@Controller('reminders')`)

All endpoints are scoped to the dashboard user (`getDashboardUserId`).

| Method | Path | Behavior |
| --- | --- | --- |
| GET | `/api/reminders?status=upcoming\|done` | `getUserReminders(userId, status)`. `upcoming` (default when absent, so the bot `/reminders`, the Home payload and old clients are unchanged): `getUserUpcomingReminders`, rows with `isTriggered = false`, `remindAt` ASC. `done`: `getUserDoneReminders`, rows with `isTriggered = true` (every time sent, or marked done), `completedAt` DESC NULLS LAST then `remindAt` DESC, at most `REMINDER_LIST_LIMITS.DONE_MAX` = 200 (no paging yet). Other value ⇒ 400 `status is invalid.` (`reminderListStatus`). Each row adds `chatName` (`ReminderTargetService.chatNames`) and `remindTimes` (earliest first) |
| GET | `/api/reminders/:id` | One reminder of the user, 404 otherwise |
| POST | `/api/reminders` | Requires `title` and `remindTimes` (≤10; ISO strings or `{ remindAt, repeatType?, repeatWeekdays? }`) or a single `remindAt`; optional `notifyType` (`text`/`call`), legacy `repeatType`, `nagEveryMinutes` + `nagCount`, `chatId`, `remindUserIds`, `remindMode` |
| PATCH | `/api/reminders/:id` | Updates `title`, `remindTimes` (or legacy `remindAt` = one time), `notifyType`, legacy `repeatType`, `nagEveryMinutes` / `nagCount` (`null` = off), target fields. New times put a finished reminder back to pending; a target change alone does not |
| DELETE | `/api/reminders/:id` | Returns `{ deleted: true }`, 404 if not found |

Contracts: `IReminderListItem` (+ `chatId?`, `chatName?`, `remindUsers?`, `remindMode?`, `completedAt?`), `REMINDER_LIST_STATUSES` / `ReminderListStatus` / `isReminderListStatus`, `REMINDER_LIST_LIMITS`, `ICreateReminderRequest`, `IUpdateReminderRequest` (+ `chatId?`, `remindUserIds?`, `remindMode?`) (`@zalobot/contracts`). The controller ignores `status`/`snoozeCount`/`snoozedUntil` from the request body. `notifyType: 'call'` with a target other than the owner's private chat ⇒ 400.

## Scheduler (`ReminderSchedulerService`)

- BullMQ queue `reminders` (`reminder.queue.ts`), worker `ReminderProcessor` (concurrency 1), logic in `ReminderSchedulerService`; queue mechanics (scan every 30 s, retries, Redis requirement): global/backend-runtime-services.md.
- Job `scan` (`scanDueReminders`): `getDueReminders(now)` = `reminder_times` rows with a send due (see [Repeat & remind again](#repeat--remind-again)), of reminders with `is_triggered = false`; oldest first, 50 per scan.
- The scan is skipped while ZCA is logged out (`ZcaMessengerService.isConnected()`), so reminders wait for the next login instead of being marked sent without going out.
- For each due time: `claimReminderTime(time, now)` returns the claimed send (`ReminderOccurrence`) or null; only the claimer queues job `deliver` (`deliveryJobData`) with `jobId = reminder-time-<timeId>-<ms>[-nag-<k>]`, then `refreshReminderSummary`. If queueing fails, `releaseReminderTime(timeId, occurrence)` so the next scan retries it.
- Job `deliver` (`deliverReminder`): re-reads the time (`getReminderTime`); reminder deleted ⇒ `skipped`. ZCA logged out since the scan ⇒ release the time + `refreshReminderSummary` (`released`) so the first scan after login re-queues it. Else format the fired occurrence in `Asia/Ho_Chi_Minh` with the user's `preferredLocale`, send `reminder.header.text` + title + time via `ReminderTargetService.deliver(reminderTarget(row), …)` (target = `chat_id` or the owner's private chat; people tagged or messaged privately per mode). `failed` ⇒ BullMQ retries (5 attempts, backoff from 30 s). Rows created by `dashboard-owner` before reminder targets point at `dashboard-owner` and are skipped (they never reached anyone before either).
- `refreshReminderSummary`: `reminders.remind_at` = the next send (time not sent or reminder again); with none left ⇒ `isTriggered=true`, `status='completed'`, `completedAt`; also writes the legacy `repeat_type`. Reminders with a repeating time never run out of sends.
- Known gap: `notifyType = 'call'` is stored and displayed, but the scheduler always sends a text message (no call path; `reminder.header.call` is unused).

## Chat creation & confirmation

- `SET_REMINDER` is an LLM tool (`ZALO_TOOL_DEFINITIONS`); in ZCA groups it is reachable only from messages that mention the bot or use a thread prefix.
- Web model (`apps/web/src/modules/reminders/model/reminder-target.ts`): `buildReminderTargetFields` ⇒ `channelRequired` (no chat) or `usersRequired` (group without people); `REMINDER_TARGET_ERROR_MESSAGES` maps them to i18n keys for inline-edit toasts; `privateRecipient(channels, chatId)` names the person of a private chat. `reminder-create-form.ts` returns `usersRequired`.
- Times from chat: `requestedTimesFromArgs` (`zca/text/reminder-target-args.util.ts`): `remindTimes` / `remindAt` are once, each `repeatingTimes` item `{ at, repeatType, repeatWeekdays? }` adds or sets the repeat of its time ("8h hằng ngày và 14h thứ 7 tuần này"); `nagRuleFromArgs` takes `nagEveryMinutes` + `nagCount` (dropped when out of range). The payload stores `remindTimes: [{ at, repeat? }]`; `parseReminderPayload` revives it (`revivePayloadTimes`, plus a legacy whole-reminder `repeatType` of older payloads). The card shows each time with its repeat (`formatRemindTimesVN`) and a `Nhắc lại` row; the summary `🔁 nhắc lại mỗi 15 phút ×3`.
- Target from chat (`SetReminderToolStrategy`): stays the sender's private chat unless the message tags people (`AgentInput.taggedUsers`, from `extractTaggedUsers` in `zca-bot-feature.service.ts`: Zalo mentions minus the bot and `@All`) or the LLM sets `remindInGroup` ("nhắc cả nhóm"); then `chatId` = this chat, people = `reminderUsersOrSender` (`zca/text/reminder-target-args.util.ts`): the tagged ones (+ the sender with `remindSelf`), or the sender alone when nobody is tagged ("nhắc cả nhóm" without tags tags the sender); a private chat (`chatId === senderId`) gets no people, `remindMode: 'direct'` for "nhắn riêng". The payload also carries `originChatId` (trusted chat). The card shows `Gửi tới`, `Nhắc ai`, `Cách nhắc`; the summary adds `👤 @A, @B (nhắn riêng)`. Editing a pending reminder (`edit <code>`) re-runs the tool on the edit text, which carries no tags, so its people are dropped.
- The pending action is stored in Redis as JSON; on confirm, `parseReminderPayload` (`apps/api/src/zca/confirmation/transaction-confirmation.service.ts`) revives `remindAt` from ISO string into a `Date` (`toValidReminderDate` in `reminders.service.ts`) and the target fields (`parseTargetUsers`) before `RemindersService.createReminder`.
- Fast-path `/reminders` (`RemindersQuickToolStrategy`) lists upcoming reminders in chat.
